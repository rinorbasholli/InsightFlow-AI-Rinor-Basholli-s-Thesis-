\section{Client application}
\label{sec:impl-client}

The client is a single-page React application. On start it calls \path{/api/whoami}; if the call fails, it shows the login form (Figure~\ref{fig:ui-login}). After sign-in, a sidebar switches between the dashboard and the three laboratories (Figures~\ref{fig:ui-dash}--\ref{fig:ui-adv}). The client stores no data persistently and every analytical view displays the \texttt{source} label received from the server; a missing or unknown label is shown as a fallback, and the adversarial view refuses to show values that do not carry \texttt{source: computed}.

\section{Authentication and sessions}
\label{sec:auth}

% src: labSecurity.ts:21-174
Access control is implemented in \texttt{labSecurity.ts}. Credentials are read from the environment variables \texttt{LAB\_BASIC\_USER} and \texttt{LAB\_BASIC\_PASS}. They are compared with a wrapper around Node's \texttt{crypto.timingSafeEqual}, which first rejects empty values and values of different length, so that comparison time does not reveal how many leading characters were correct (NFR3). A successful login creates a session token of 24 random bytes, stored in a server-side map with a 12-hour expiry and sent to the browser in an \texttt{HttpOnly}, \texttt{SameSite=Lax} cookie, with the \texttt{Secure} flag in production (NFR4). HTTP Basic authentication is accepted as an alternative for scripted clients. Failed attempts through either path are counted per client address; after 10 failures within 15 minutes, further attempts from that address receive HTTP~429, which bounds password guessing against the shared credentials (NFR11).

The middleware \texttt{requireLabAccess} enforces three rules. In production, if either credential is missing, it answers every request with HTTP~503 and the laboratory remains closed; in development, missing credentials leave the laboratory open so that it can be run locally. When credentials are set, static assets and the login route are public and every other \path{/api/} route requires a session or valid Basic credentials. A shared credential pair, rather than per-user accounts, was chosen because the laboratory has a single role and a small group of users (learners and examiners in one course); institutional single sign-on was considered but would have tied the demonstrator to one university's identity provider.

\section{Request limits and prompt handling}
\label{sec:limits}

% src: labSecurity.ts:4-11, 176-224; server.ts
JSON bodies are limited to 32\,kB (NFR1). The limit is well above the size of a teaching email and of every request the client sends, and it bounds the amount of text that can be forwarded to the LLM in a single call. The rate limiter keeps, for each pair of client address and path, the timestamps of the requests made in the last hour and rejects further \texttt{POST} requests with HTTP~429 once the limit is reached (NFR2). The generation route is limited to 10 requests per hour because it consumes LLM quota and is the route with the highest potential for misuse; other routes allow 40. The client address is Express's \texttt{req.ip}. By default no proxy is trusted, so it is the socket peer and cannot be set by the client; behind a reverse proxy, \texttt{TRUST\_PROXY} must be set to the number of trusted hops so that \texttt{req.ip} is taken from the entry appended by the proxy rather than from a value supplied by the client.

Prompt handling differs by route because the routes receive different kinds of text. The generation and deepfake routes receive instructions written by the user; all of their fields that are inserted into the prompt are checked with \texttt{promptLooksInjected}, which rejects text matching three patterns associated with direct prompt injection~\cite{perez2022ignore}: ``ignore previous/prior/above instructions'', ``you are now'' and ``disregard the system/developer''. The analysis route receives an email written by a third party, which is the indirect case described by Greshake et al.~\cite{greshake2023signed}. Rejecting emails that contain such phrases would also reject legitimate messages, so the email is instead enclosed between explicit markers and the prompt instructs the model to analyse, not obey, the enclosed text. On all routes, the model is asked for structured output conforming to a JSON response schema; the server parses the answer and normalises the predicted class name, but does not otherwise validate the values against the schema. These measures reduce, but do not eliminate, the risk of prompt injection; Section~\ref{sec:limits-disc} discusses the residual risk.

\section{Phishing laboratory}
\label{sec:impl-phish}

\paragraph{Teaching material.} \texttt{academicDataset.ts} contains three authored exemplars (one per class), four reconstructions of publicly documented scam and notice patterns (a credential-harvest lure, business email compromise, a parcel-fee lure and a legitimate library notice), and the function \texttt{generate90Samples}. The function uses a Mulberry32 pseudo-random generator with the fixed seed 20260927, so the same 90 emails (30 legitimate, 30 conventional phishing, 30 AI-style phishing) appear on every load. The first three are the authored exemplars with fixed scores; the scores of the other 87 are drawn uniformly from bands configured for each class, shown in Table~\ref{tab:bands}. All of them are teaching values, not measurements.

\paragraph{Generation and analysis.} The generation and analysis routes call Gemini with \texttt{responseMimeType: application/json} and a response schema, so the client receives typed fields (for example \texttt{realismScore}, \texttt{indicators} and \texttt{predictedCategory}) without a second parser. The analysis prompt asks for a predicted class among \texttt{legitimate}, \texttt{conventional\_phishing} and \texttt{ai\_phishing}, and states that the answer is an LLM judgement, not a spam-filter measurement; the server normalises the returned class name. If the Gemini call throws, the generation route returns a fixed template and the analysis route returns the result of a keyword heuristic that inspects the sender domain, look-alike host names and urgency or payment terms. Both fallbacks are labelled \texttt{source: fallback}.

\paragraph{Email files.} \texttt{parseEmailFile} reads a \texttt{.txt} or \texttt{.eml} file in the browser, unfolds header continuation lines, and extracts \texttt{From}, \texttt{To} and \texttt{Subject} from the header block and the body after the first blank line. The file itself is not uploaded; only the extracted fields are sent for analysis. Figure~\ref{fig:ui-phish} shows the laboratory.

\section{Deepfake laboratory}
\label{sec:impl-df}

% src: server.ts (PRE_BAKED_DEEPFAKES, getDynamicFallbackDeepfake)
The deepfake laboratory analyses scenarios, not files. Three presets represent common social-engineering cases: an executive video requesting an urgent transfer, a voicemail requesting confidential data, and an identity-document image. When the filename matches a preset exactly, the server returns stored teaching content: visual and audio irregularities to look for, markers with a category (physical, temporal, acoustic or digital), and defences such as out-of-band verification and content-provenance checks~\cite{c2pa2spec}. For any other filename, Gemini writes a comparable analysis from the filename, media type and description; if Gemini is unavailable, a fallback assembles generic markers according to the media type. The marker confidences in all three cases are part of the teaching content, not detector outputs, and the user interface states that media bytes are not inspected (Figure~\ref{fig:ui-df}).

Shipping a detector was considered and rejected. Detectors trained on public benchmarks generalise poorly to real recordings~\cite{muller2022audio}, artefact-based cues such as blinking become obsolete as generators improve~\cite{li2018ictu}, and running a detector would have required accepting and storing user media, with the associated privacy obligations. A scenario module with explicit provenance teaches the defensive procedures, which remain valid regardless of the quality of the forgery.

\section{Adversarial laboratory}
\label{sec:impl-adv}

\paragraph{Model.} The attack service loads the \texttt{cifar10\_resnet56} checkpoint through \texttt{torch.hub} from the \texttt{pytorch-cifar-models} repository~\cite{chenyaofo2021cifar}. A ResNet-50 pretrained on ImageNet was considered but rejected: it expects $224 \times 224$ inputs and a 1000-class output, so attacking it on CIFAR-10 would require resizing the images and mapping label spaces, and clean accuracy would then reflect those adaptations as much as the model. A network trained on CIFAR-10 allows clean and robust accuracy to be measured on the same $32 \times 32$ inputs. Inputs are kept in pixel space $[0,1]$, and normalisation with the CIFAR-10 channel means and standard deviations is applied inside the forward function, so that $\varepsilon$ is expressed in pixel units.

\paragraph{Attack implementation.} FGSM and PGD share one function, \texttt{run\_local\_attack}, used by both the live service and the batch evaluation (Listing~\ref{lst:attack}). FGSM is a single step of size $\varepsilon$ (Equation~\ref{eq:fgsm}); PGD performs 10 steps of size $\alpha = \varepsilon/4$ from the clean image, without random initialisation. After every step the perturbed image is projected onto the $L_\infty$ ball of radius $\varepsilon$ around the original and clipped to $[0,1]$. A targeted variant descends the loss of a chosen target class instead of ascending the loss of the true class.

% src: eval/adversarial/run_attacks.py:45-63
\begin{lstlisting}[language=Python,float=htbp,caption={Shared FGSM/PGD implementation (\texttt{eval/adversarial/run\_attacks.py}, abridged).},label=lst:attack]
def project_linf(x_adv, x0, eps):
    return torch.max(torch.min(x_adv, x0 + eps), x0 - eps).clamp(0.0, 1.0)

def run_local_attack(model, x, y, eps, method="fgsm", target=None, steps=10):
    label = target if target is not None else y
    sign = -1.0 if target is not None else 1.0
    alpha = eps if method == "fgsm" else eps / 4
    n = 1 if method == "fgsm" else steps
    x0 = x.detach()
    x_adv = x0.clone()
    for _ in range(n):
        x_adv = x_adv.detach().requires_grad_(True)
        F.cross_entropy(logits(model, x_adv), label).backward()
        x_adv = x_adv.detach() + sign * alpha * x_adv.grad.sign()
        x_adv = project_linf(x_adv, x0, eps)
    return x_adv.detach()
\end{lstlisting}

\paragraph{Live service.} % src: eval/adversarial/service.py:112-175
For each request, the service validates $\varepsilon \in (0, 0.25]$ and the class name (HTTP~400 otherwise), selects the first test image of the requested class that the model classifies correctly, and runs the attack. It then measures $\|x_{\mathrm{adv}} - x\|_\infty$ and, if the value exceeds $\varepsilon$ by more than $10^{-6}$, returns HTTP~500 instead of a result (NFR6). The response contains the clean and adversarial top-1 classes with their softmax confidences, the requested budget, the measured perturbation, the attack method, and, for targeted runs, whether the target was reached. Figure~\ref{fig:ui-adv} shows a computed untargeted FGSM result; the noise image next to it is an illustration and is labelled as such.

\section{Evaluation scripts}
\label{sec:impl-eval}

\paragraph{Phishing benchmark.} % src: eval/phishing/run_benchmark.py
\path{run_benchmark.py} builds the corpus from code (\texttt{build\_corpus}), writes it to \texttt{corpus.jsonl}, and evaluates three models: a TF-IDF (unigram and bigram, minimum document frequency 2) and logistic-regression pipeline on subject and body only (\emph{wording only}); the same pipeline with the \texttt{From} address appended (\emph{with sender}); and a constant classifier that always predicts phishing (\emph{baseline}). Each model is evaluated on a stratified 70/30 hold-out split, with stratified five-fold cross-validation, and with stratified five-fold cross-validation grouped by sender domain, so that no domain appears in both the training and the test folds; all splits use seed 20260927. Because the corpus is generated from code, rerunning the script regenerates exactly the same data and metrics (NFR7).

\paragraph{Adversarial batch.} % src: eval/adversarial/run_attacks.py:134-210
\path{run_attacks.py} draws 200 images from the CIFAR-10 test set without replacement, using seed 20260927, measures clean accuracy, and runs FGSM and PGD at $\varepsilon \in \{2/255, 8/255, 16/255\}$. For each budget it records robust accuracy with a Wilson 95\% confidence interval, attack success rate, flip rate, and mean and maximum $L_\infty$. The script stops with an error if any perturbation exceeds its budget, and it writes the generation time, the PyTorch version and the Git commit into the result file.

\section{Automated tests}
\label{sec:tests}

The test suite (\texttt{npm test}) contains 34 tests in two files and runs offline. \path{tests/labSecurity.test.ts} (28 tests) exercises the security functions directly with mock requests: constant-time comparison, rejection of empty credentials, the session-cookie attributes, session expiry after 12 hours, the failed-sign-in limit, fail-closed behaviour in production with one or both credentials missing, the open development mode, Basic authentication, the session cookie, public and protected paths, the client-address function, the 10 and 40 request limits with per-path isolation, and the injection patterns, including a set of ordinary phishing-task prompts that must \emph{not} be rejected. \path{tests/apiContract.test.ts} (6 tests) checks contracts that span files: the 32\,kB limit is wired into the server, every \texttt{source} label used in the code belongs to the documented set, all routes are registered, the language routes apply the prompt controls to every interpolated field, the proxy trust setting is configurable, the benchmark evaluates the three models, and the attack service uses the shared pixel-space implementation and refuses perturbations above $\varepsilon$. The contract tests inspect source code and result files rather than issuing HTTP requests; end-to-end tests through HTTP are not part of the suite.

\section{Problems encountered}
\label{sec:problems}

\paragraph{Perturbations above the budget.} Torchattacks~\cite{kim2020torchattacks} was initially used for the live attacks. A live call with $\varepsilon = 0.05$, recorded in the first commit of the repository (\texttt{a133834}), produced a measured $L_\infty$ of 0.205, about four times the budget. The overshoot coincided with the library's input-normalisation option, which was used because the pretrained model expects normalised inputs. Instead of depending on that interaction, the library was removed, and both paths now use the pixel-space implementation in Listing~\ref{lst:attack}, followed by an explicit check of the measured perturbation. All recorded live calls now report $L_\infty = 0.05$ at $\varepsilon = 0.05$ (Section~\ref{sec:eval-live}).

\paragraph{Sender information in the benchmark.} An early version of the benchmark appended the sender address to every training and test text while its metadata stated that the sender was excluded. The feature sets were separated into the wording-only and with-sender models described above, which also turned the problem into a finding (Section~\ref{sec:eval-phish}).

\paragraph{Corpus regeneration.} While the phishing results were being reproduced for this report, the benchmark script was found to regenerate only the 79 look-alike emails: an indentation error, introduced in a later edit, had moved the line that adds each email to the corpus inside the branch for that family. The published results had been produced before the error; after the correction, the script again reproduces the 187-email corpus and the published results exactly.

\paragraph{LLM availability.} The Gemini API occasionally returned HTTP~503 under high demand; the recorded generation call succeeded on its second attempt. The fallback design (FR10) keeps the laboratory usable when this happens and labels the result accordingly.

\section{Summary}

The implementation realises the provenance contract in each module, shares one attack implementation between demonstration and evaluation, and enforces the security requirements in middleware that is covered by automated tests. Chapter~\ref{cha:eval} evaluates the result.
