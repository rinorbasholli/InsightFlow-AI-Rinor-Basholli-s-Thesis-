\chapter{Architecture and design}
\label{cha:arch}

This chapter presents the design that realises the requirements of Chapter~\ref{cha:req}. It describes the component architecture and the reasons for it, the deployment options, the mapping of components to the repository, the data model, the main interaction sequences, the API contracts and the security controls in the request path.

\section{Architecture overview}
\label{sec:arch-overview}

The laboratory is a client--server system with a separate computation service (Figure~\ref{fig:arch}). A React single-page application runs in the browser and communicates only with an Express server. The server enforces authentication and limits, calls the Gemini API for the language tasks, and forwards attack requests to a Python service built with FastAPI, which holds the pretrained CIFAR-10 model.

Three alternatives were considered. A notebook-based design (one notebook per risk) would have been simpler to build, but would not provide an authenticated, shared application in which the three risks appear in one workflow, which is the gap identified in Section~\ref{sec:gap}. Running the attacks inside the Node.js process was rejected because PyTorch and the pretrained models are native to Python, and because coupling a heavy, slow computation to the web server would make the whole site unavailable whenever the model is loading or the computation fails. Calling the LLM directly from the browser was rejected because it would expose the API key and bypass the server-side limits. The chosen split isolates each concern: the web server can run without the attack service, and the attack service can be restarted without taking the website down (NFR8).

\section{Deployment}
\label{sec:deploy}

The repository supports two deployment configurations. In development, \texttt{npm run dev} starts Express with the Vite middleware on port 3000, and the attack service is started separately on port 8001. For production, a container image is built from \texttt{Dockerfile}: it compiles the client with Vite, bundles the server with esbuild, and runs \texttt{node dist/server.cjs} with \texttt{NODE\_ENV=production} on port 8080 (NFR10). A second image, \path{deploy/Dockerfile.all-in-one}, adds Python 3.12 and PyTorch and starts both processes in one container, so that the adversarial module is available in a single deployment. The script \path{deploy/start-live-lab.sh} reproduces this configuration locally and refuses to start when the access credentials are missing. When a platform places a reverse proxy in front of the container, \texttt{TRUST\_PROXY=1} must be set so that rate limiting uses the client's address rather than the proxy's.

Sessions and rate-limit counters are kept in process memory (Section~\ref{sec:arch-sec}). The design therefore assumes a \emph{single instance} of the server. If a hosting platform runs several instances behind a load balancer, each instance holds its own sessions and counters, so a user may be asked to sign in again and the effective rate limit is multiplied by the number of instances. Section~\ref{sec:limits-disc} lists this as a limitation.

\section{Data model}
\label{sec:data-model}

The laboratory has no database. Runtime state lives in the browser, and the evaluation results are files written by the scripts.

\paragraph{Client state.} The application keeps the active screen, the most recent analysis and the list of analysed emails in React state (Figure~\ref{fig:data}). Each email record carries its scores together with two provenance fields: \texttt{analysisSource} records whether the scores come from the seeded dataset, from Gemini or from the fallback, and \texttt{labelOrigin} records where the class label came from. Clearing the dashboard empties the list; reloading the page discards it.

The email-analysis sequence has the same shape, with one difference in prompt construction: the email is treated as untrusted third-party data. The server encloses it between explicit markers and instructs the model not to follow instructions found inside it (Section~\ref{sec:limits}). The deepfake sequence adds a branch before the external call: if the filename equals one of the three presets, the server returns the stored analysis with \texttt{source=preset} and Gemini is not called.

Figure~\ref{fig:seq-adv} shows the adversarial sequence. It is the only path whose numbers are computed by a model, and it has no fallback: if the attack service cannot be reached, the server answers with HTTP~503.

\section{API contracts}
\label{sec:api}

Table~\ref{tab:api} specifies the HTTP interface. All routes except \texttt{POST /api/login} and \texttt{POST /api/logout} require a valid session cookie or HTTP Basic credentials and otherwise return HTTP~401. All \texttt{POST /api/} routes are rate limited (HTTP~429) and limited to 32\,kB of JSON (HTTP~413).

The attack service exposes \texttt{GET /health}, \texttt{GET /summary} and \texttt{POST /attack}. When the environment variable \texttt{EVAL\_INTERNAL\_TOKEN} is set, the service requires it in the \texttt{X-Eval-Token} header and the Express server forwards it, so that the service cannot be called directly by other hosts.

\section{Security controls in the request path}
\label{sec:arch-sec}

Every request passes three middleware functions before reaching a route: the JSON body limit, \texttt{requireLabAccess} and \texttt{rateLimitApi}. \texttt{requireLabAccess} fails closed: in production, if either credential is missing, every request receives HTTP~503. Static assets and the login page are public so that the login form can render; every API route except login and logout is protected. Rate-limit counters are keyed by client address and path, where the client address is taken from Express's \texttt{req.ip}. By default no proxy is trusted, so \texttt{req.ip} is the socket peer; when the laboratory runs behind a reverse proxy, the environment variable \texttt{TRUST\_PROXY} is set to the number of trusted proxy hops. Failed sign-in attempts are counted per client address as well. The language routes add prompt-level controls described in Section~\ref{sec:limits}. Section~\ref{sec:stride} relates these controls to the STRIDE threat categories.

\section{Summary}

The architecture separates presentation, policy enforcement, language tasks and numerical computation into components that can fail independently. The next chapter describes how each component was implemented.
